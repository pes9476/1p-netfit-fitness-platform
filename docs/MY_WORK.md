# 박은서의 NetFit 작업 상세 기록

> NetFit 팀 프로젝트에서 제가 맡은 작업을 **기획 → 문제 → 해결 → 결과** 순서로 정리한 문서입니다.
> 각 작업 끝의 **"설명 포인트"**는 이 작업을 다른 사람에게 설명할 때 꼭 알아야 하는 개념을 정리한 것입니다.
>
> 개발 방식: 문제 정의, 화면 설계, 결과 검수, 배포 판단은 직접 했고, 코드 구현에는 AI 코딩 도구를 함께 활용했습니다.

## 1. Django 서비스 뼈대와 화면 구조 설계

### 기획
공모전 서비스의 핵심 흐름은 **로그인 → 내 신체 정보로 캐릭터 만들기 → 운동 기록 → 배지·포인트 획득 → 친구·파티와 경쟁 → 아이템으로 꾸미기**였습니다. 팀원 4명이 각자 기능을 붙일 수 있도록, 이 흐름을 먼저 화면과 데이터 구조로 나눴습니다.

### 작업
- `config`(프로젝트 설정)와 `fitness`(서비스 앱) 구조 생성
- 공통 레이아웃 `base.html`: 상단 바(일일 미션, 튼튼머니, 새 파티, 그룹원, 친구) + 7개 메뉴(대시보드, 마이페이지, 운동 기록, 랭킹, 친구, 주변 시설, 메달 샵)
- 온보딩 6단계 화면: `intro → profile → course → mode → solo / group → group_quest`
- 기본 모델: 프로필(신체 정보, 캐릭터), 운동 기록, 파티, 개인/파티 미션, 배지, 아이템 구매
- NetFit 네온 테마 CSS, 마스코트 선택 화면, 튼튼머니 팝업

### 결과
이후 팀원의 기능(카카오 로그인, 실시간 날씨·뉴스, 파티 챌린지, 핏봇 이중 엔진, DB 연동)이 모두 이 뼈대 위에 추가됐습니다.

### 설명 포인트
- **Django의 MTV 구조**: Model(데이터 구조) / Template(화면 HTML) / View(요청을 받아 데이터를 꺼내 화면에 넘기는 함수)
- **URL 라우팅**: `fitness/urls.py`에서 주소마다 어떤 view 함수가 실행될지 연결
- **템플릿 상속**: 모든 화면이 `base.html`을 상속해서 상단 메뉴를 한 번만 만들어도 전체 화면에 적용됨

## 2. 공공 체육시설 데이터 → '주변 시설' 화면

### 기획
대회 주제가 **공공데이터 활용**이었기 때문에, 서비스 안에서 공공데이터가 실제로 쓰이는 화면이 필요했습니다.

### 작업
- 국민체육진흥공단의 **'전국 공공체육시설 현황'** 데이터를 찾아 CSV(약 4.5만 건)로 확보
- CSV를 DB의 시설(Facility) 테이블로 불러오는 관리 명령 `python manage.py import_facilities <csv경로>` 작성
- 시설 목록을 보여주는 **'주변 시설' 화면** 구성

### 이후 팀원 작업과의 연결
- 팀원: 시설 데이터 검증·중복 방지·실행 기록 같은 ETL 구조 설계
- 팀원: 운동 기록 화면의 위치 기반 시설 추천, 실시간 운영시간·휴무 표시, URL 다운로드 자동 동기화

### 설명 포인트
- **Django 관리 명령(management command)**: `manage.py` 뒤에 붙여 실행하는 나만의 명령. 데이터 적재처럼 화면 없이 한 번씩 돌리는 작업에 사용
- CSV의 각 행을 읽어 `Facility` 모델 객체로 저장하는 구조

## 3. 캐릭터 이름 통일과 핏봇 Gemini 전환

### 기획
캐릭터를 동물 종류가 아닌 고유한 이름으로 부르고, 홈페이지와 챗봇에서 같은 이름이 나오게 하고 싶었습니다. 또 챗봇이 운동 질문에 실제로 답해야 했습니다.

### 문제
- 캐릭터 이름이 챗봇, 회원가입, 친구, 피팅룸 등 여러 화면에 흩어져 있어 한 곳만 바꾸면 화면마다 이름이 달라질 수 있었습니다.
- 팀에서 무료 **Gemini API 키**를 준비해 등록했지만 "AI 연결 설정이 필요합니다" 오류가 계속 나왔습니다. 당시 챗봇 코드는 **Groq**라는 다른 AI 서비스를 호출하고 있었습니다. 준비된 키와 호출하는 서비스가 달랐던 것입니다.

### 해결
- 이름을 **백호 / 포동(백곰) / 토리(햄스터) / 아콩(아기공룡)**으로 정하고, 이름이 나오는 모든 화면(챗봇 위젯, 회원가입 폼, 모델, 친구·홈·온보딩·프로필 화면)과 관련 테스트를 한 번에 수정했습니다.
- 오류 화면과 재현 상황을 정리해 원인을 좁히고, 챗봇이 Gemini API(`generativelanguage.googleapis.com`)를 호출하도록 전환했습니다. 작업 대상도 테스트 브랜치가 아닌 **운영 브랜치(`runsv`)**로 명확히 해 실제 사이트에 반영되게 했습니다.

### 이후
팀원이 Groq와 Gemini를 자동으로 번갈아 쓰는 이중 엔진과 오류 진단 기능을 추가했습니다.

### 설명 포인트
- **문자열을 여러 곳에서 쓸 때의 문제**: 한 곳만 바꾸면 화면마다 이름이 달라짐 → 바꿀 때는 전체 검색으로 범위를 정해 한 번에 수정
- **API 키**: 외부 서비스를 쓸 권한이 있는지 확인하는 값. 서비스마다 따로 발급되므로, 키와 호출하는 서비스가 맞는지부터 확인해야 함

## 4. ⭐ 캐릭터 아이템 착용 렌더러 개선

### 기획
메달 샵에서 산 아이템(헤어밴드, 선글라스, 헤드셋, 마스크, 벨트, 글러브, 모자, 왕관 등 16종)을 4종 캐릭터에 **실제로 입힌 것처럼** 보여줘야 했습니다. 특히 **밴드는 이마, 선글라스는 눈, 헤드셋은 귀**에 있어야 하고 셋을 동시에 착용할 수 있어야 했습니다.

### 문제
- 아이템이 캐릭터 얼굴 위에 떠 있거나, 밴드·마스크·목걸이가 얼굴 한가운데 뭉쳐 보였습니다.
- 원인: 동물마다 얼굴·귀·몸 위치가 다른데, **아이템 이미지를 따로 잘라 캐릭터 위에 같은 좌표로 얹고**, 움직임 애니메이션도 따로 적용하고 있었습니다.

### 실패한 시도
1. 캐릭터별로 위치·크기 보정값을 하나씩 추가 → 한 조합을 맞추면 다른 조합이 틀어짐
2. 이전 코드로 복구 → 마지막 커밋에 이미 수정 코드가 섞여 있어 복구 기준 자체가 불분명했음

### 해결
- **새 기준**: 아이템을 따로 움직이지 않는다. 이미 캐릭터에 딱 맞게 착용된 상태로 그려진 **원본 이미지**를 쓰고, 그중 필요한 부위만 보여준다.
- 모든 캐릭터를 **같은 627×627 좌표 칸**에서 다루고, 캐릭터별·아이템별로 "보여줄 영역(다각형 좌표)"을 정의
- SVG `clipPath`로 그 영역만 잘라 캐릭터 위에 겹침 → 캐릭터와 아이템이 **같은 좌표, 같은 움직임**을 공유
- 아이템 레이어 순서를 고정해 **어떤 순서로 착용해도** 앞뒤 관계가 같게 함
- 검수 중 발견한 "벨트가 운동복까지 덮는 문제"는 벨트 영역 경계를 좁혀 해결
- 실제 피팅룸과 **같은 렌더러 코드**를 쓰는 로컬 미리보기 페이지(`docs/outfit-preview.cjs`)를 만들어, 포인트를 쓰거나 구매하지 않고도 모든 조합을 확인

### 검수
- 화면 확인: 4개 캐릭터 × 밴드·선글라스·헤드셋 단독/동시 착용, 밴드+마스크+목걸이, 운동복+벨트+글러브, 날개+망토+검, 모자·왕관
- 자동 테스트 3건 통과 (`node --test fitness/test_outfit_renderer.cjs`)
  1. 16종 아이템이 4개 캐릭터 모두에서 그려지는지
  2. 착용 순서와 관계없이 레이어 순서가 같고, 벗으면 흔적이 남지 않는지
  3. 여러 캐릭터를 한 화면에 그려도 SVG ID가 충돌하지 않는지

### 결과
착용 상태가 **피팅룸, 대시보드 캐릭터 카드, 마이페이지**에 똑같이 반영되도록 연결하고 운영 사이트에 배포했습니다.

### 설명 포인트
- **SVG와 clipPath**: SVG는 코드로 그리는 이미지 형식. `clipPath`는 "이 모양 안쪽만 보여줘"라는 마스크
- **왜 이 방식이 나았나**: 보정값을 계속 더하는 방식은 경우의 수(캐릭터 4 × 아이템 16 × 조합)가 늘수록 깨짐. 원본 착용 위치를 기준으로 삼으면 기준점이 하나라 일관됨
- **회귀 테스트**: 고친 것이 나중에 다시 깨지지 않는지 자동으로 확인하는 테스트

## 5. 종료된 파티가 메뉴에 남는 버그 수정

### 문제
내기 기간이 끝난 파티가 상단 '그룹원' 메뉴에 계속 보였습니다. 새로고침해도 그대로였습니다.

### 해결 과정
1. **1차 수정** (`ca2ac6e`): 모든 화면에 공통 데이터를 넘기는 `context_processors.py`에서 종료일이 오늘 이전인 파티를 제외
2. **문제 재발견**: 진행 중인 파티가 하나도 없으면 오히려 전체 파티가 다시 나타남
3. **원인**: 템플릿의 `{% for party in header_user_parties|default:user.parties.all %}`
   → 필터링한 목록이 **비어 있으면** `default`가 전체 파티 목록으로 바꿔 버림
4. **2차 수정** (`42dfa45`): `default` 대체 경로를 제거하고 "빈 목록일 때도 종료 파티가 안 보이는지" 테스트 추가
5. 화면에서 숨기기만 했고, 파티와 회원 데이터는 삭제하지 않았습니다.

### 설명 포인트
- **context processor**: 모든 템플릿에 자동으로 같은 데이터를 넣어주는 Django 기능. 상단 메뉴처럼 모든 화면에 나오는 정보에 사용
- **템플릿 필터 `default`**: 값이 비어 있으면(빈 리스트 포함) 대신 쓸 값을 정함 → 편리하지만 이번처럼 의도하지 않은 대체가 일어날 수 있음

## 6. Render 운영 배포와 배포 검수

### 작업
- 처음에 쓰던 Railway 배포 설정 파일을 정리하고 **Render 기준으로 통일** (`render.yaml`, `config/settings.py`)
- 브랜치 운영 규칙: `testsv`(테스트·개발) → 검증 후 `runsv`(운영, Render 자동 배포)

### 문제: 푸시 거절
아이템 수정을 배포하려고 푸시했는데 거절됐습니다. 그사이 팀원이 운영 브랜치에 새 커밋을 올렸기 때문입니다.

### 해결
1. 강제 푸시(`--force`)는 팀원 작업을 지울 수 있어 사용하지 않음
2. 원격 최신 커밋을 받아 **내 변경 파일과 겹치는지** 확인 → 겹치지 않음
3. 내 커밋을 최신 커밋 위로 다시 올린 뒤(rebase) 테스트를 다시 돌리고 일반 푸시
4. Render에서 `Deploy succeeded | Live` 확인
5. `/healthz/`(서버 상태 확인 주소), 새 렌더러 JS, 새 아이템 이미지가 **HTTP 200**으로 응답하는지 확인

### 설명 포인트
- **merge vs rebase**: merge는 두 갈래를 합치는 커밋을 하나 더 만들고, rebase는 내 커밋을 최신 위치로 옮겨 이력을 한 줄로 만듦
- **헬스 체크**: 서버가 살아 있는지 확인하는 간단한 주소. 배포 직후 "사이트가 정상인지"를 빠르게 확인하는 용도

## 회고

### 배운 점
- 모호한 요구("자연스럽게")를 **캡처와 구체적 기준**("밴드는 이마, 안경은 눈, 헤드셋은 귀")으로 바꾸면 수정과 검수가 훨씬 빨라진다.
- 로컬에서 고친 것, Git에 올린 것, 운영 사이트에 반영된 것은 **각각 따로 확인**해야 한다.
- 팀 작업에서는 내 작업을 올리는 것만큼 **다른 사람의 최신 작업을 지키는 것**이 중요하다.

### 아쉬운 점과 다음 계획
- 수정 전 정상 화면과 커밋을 기록하지 않아 복구 기준이 불명확했다 → 다음에는 **수정 전 기준 화면·승인 조건을 먼저 정하고** 시작한다.
- 모든 아이템 조합, 다양한 화면 크기(모바일), 이미지 로딩 속도까지는 검수하지 못했다.
- AI 코딩 도구가 만든 코드를 검수하면서, 결과 화면뿐 아니라 **코드가 왜 그렇게 동작하는지 이해하는 것**의 중요성을 느꼈다. 다음 프로젝트에서는 핵심 로직을 직접 설명할 수 있을 때까지 확인한 뒤 반영한다.
